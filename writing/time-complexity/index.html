Can you find the time complexity?

2023-01-15 · Originally published on Codeforces

Hello, Codeforces!

I want to share with you 2 problems that I was not able to find a tight time complexity / bound for. After trying for a while, I decided to ask here, maybe someone can help me.

Problem 1

We want to maintain a collection of arrays of integers in [0,U)[0, U)[0,U) represented with binary search trees, such as Treaps. We will have qqq updates, which can be one of the following:

  1. Split an array by position;
  2. Concatenate two arrays;
  3. Reverse an array;
  4. Split an array by value.

Of course, it is well known how to support operations (1), (2) and (3) each in O(log⁡n)\mathcal O(\log n)O(logn), if nnn is the total size of the collection.

What is interesting here is operation (4). Going into more detail about what it means, given an array and some value xxx, we want to split this array into two: one containing values that are smaller than xxx in the same order as they were, and the other containing values that are at least xxx, also in the same order as they originally were. This is equivalent to running

std::stable_partition(v.begin(), v.end(), [&](int k) { return k < x; });

My proposed solution to implement this is to repeatedly split the array at the first position that has value smaller than xxx, then split at the first position that has value at least xxx, and repeat. It would look like this

void treap::partition(int x) {
	treap small, big;
	while (size()) {
		treap tmp;
		split(first_not_smaller(x), tmp);
		small.concat(tmp);
		split(first_smaller(x), tmp);
		big.concat(tmp);
	}
	// Now the elements are split into small and big,
	// and this treap is empty
}

The number of splits this algorithms does is the number of positions such that a “small” element and a “big” element are adjacent in the array.

Example

If a=we have an array a=[2,3,5,7,8,1,3,6,4]a = [2, 3, 5, 7, 8, 1, 3, 6, 4]a=[2,3,5,7,8,1,3,6,4], after applying operation (4) with x=4x = 4x=4, we would split the array like the following

[2,3∣5,7,8∣1,3∣6,4][2, 3 | 5, 7, 8 | 1, 3 | 6, 4][2,3∣5,7,8∣1,3∣6,4]

So we did 3 splits. We would then concatenate these pieces to get the small array [2,3,1,3][2, 3, 1, 3][2,3,1,3] and the big array [5,7,8,6,4][5, 7, 8, 6, 4][5,7,8,6,4].

Of course, this can be linear in the worst case, but can you find an instance such that this algorithm does Θ(q∗n)\Theta(q * n)Θ(q∗n) splits? My guess is that this algoriths does at most O(log⁡U)\mathcal O(\log U)O(logU) splits, amortized. But I was not able to prove this.

I have tried a few potential functions, such as the sum of logs of gaps between adjacent values in the arrays, but they did not work.

Problem 2

It turns out that a bound for this problem implies a bound for the previous problem, if we implement it in a specific way.

Imagine that there are nnn coins, arranged in some piles in an arbitrary way. We will do nnn operations. In each operation, we choose some number k>0k \gt 0k>0, and choose kkk non-empty piles. For each of these piles, we choose a non-zero number of coins to take from it. All of the coins we took are arranged in a new pile.

The cost of the operation is kkk (note that it is not the total number of coins, but the number of piles).

If we have the freedom to choose our operations in any way we like (and also the starting configuration), what is the maximum cost we can achieve? I could not find an instance that took Θ(n2)\Theta(n^2)Θ(n2). However it is easy to create an instance that takes Θ(n∗n)\Theta(n * \sqrt n)Θ(n∗n​).

Sqrt instance

Assume nnn is a triangular number, that is, n=1+2+⋯+xn = 1 + 2 + \dots + xn=1+2+⋯+x. Now we will have piles with 1, 2, 3, …, xxx coins. In each operation we take one coin from each pile. We can see that after the operation the configuration is the same, so we can keep repeating this operation of cost x∈Θ(n)x \in \Theta(\sqrt n)x∈Θ(n​).

Fun observation

I noticed that, if nnn is a triangular number, any initial configuration applied repeatedly with the operation of taking one coin from each pile eventually falls in the instance above, that is, sizes of piles eventually become 1, 2, 3, …, xxx. I could not prove that this always happens.

We think the maximum cost is O(n∗n)\mathcal O(n * \sqrt n)O(n∗n​), but we could not prove it. We managed, however, to prove this bound if we restrict the operation a bit: if we only allow to take at most one coin per pile.
